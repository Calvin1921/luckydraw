# What comes next

The priority is a host who can operate the event confidently, including when something goes wrong. These are known gaps and proposed acceptance criteria—not completed features.

| Priority | User problem | A useful completion check |
|---|---|---|
| Next | The initial stage/QR handoff is unclear. | An organizer can privately pair the host before starting a round, without guessing a URL. |
| Next | “Next Prize” does not identify the actual item. | The remote shows the next prize, round and repeat rule before DRAW. |
| Next | The organizer cannot inspect winners on screen. | A confirmed award appears in a private summary with guest, prize, round and time. |
| Next | A disconnected remote can still say “Connected.” | Offline/reconnecting states reflect the real connection, and new draw actions cannot queue unexpectedly. |
| Next | The CSV-template link is broken. | A fictional bilingual template downloads and imports with a clear accepted-row count. |
| Next | Reject does not explain whether a guest remains eligible. | Absence handling states the exclusion scope explicitly and gives a clear confirm/cancel action. |
| Before real events | Public queries expose controller capabilities. | Organizer authorization and scoped, revocable host access protect every query and mutation path. |
| Before fairness claims | Selection code and algorithm metadata differ. | The live selection is unbiased, consistently labeled and tested through its actual mutation path. |
| Later | Large participant and prize lists are hard to scan. | Search/compact participant rows and grouped prize quantities make event preparation manageable. |
| Later | Operational/accessibility confidence is incomplete. | Rehearsals cover real phones/projectors, keyboard and screen-reader use, reduced motion, reconnects and concurrent actions. |

Small contributions with a clear user outcome are welcome. See [CONTRIBUTING.md](../CONTRIBUTING.md).
